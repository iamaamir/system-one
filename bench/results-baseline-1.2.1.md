# 1.2.1 baseline (recorded after the system_one representation-repair work)

Machine: node v24.14.0 arm64 (Apple Silicon). Figures are the median of 3 runs
of the same command, measured back-to-back on one machine so the two columns are
comparable. `results-baseline-v1.2.0.md` is kept as the pre-change reference and
must not be compared against these figures directly — it was recorded on
different hardware.

Nothing in CI reads either file. They exist so a future change can tell a real
regression from machine noise.

## normalize.bench.ts — prepareSystemOneArgs()

`garbage` is generated bytes per op; `retained` is heap still live after a forced
GC, i.e. leaks. Garbage figures repeat exactly run to run; timing varies a few %.

| scenario | `main` (8cf6ba1) | 1.2.1 | delta |
| --- | --- | --- | --- |
| canonical | 651 ns/op, 290 B/op | 1415 ns/op, 1939 B/op | +117% time, +569% generated |
| canonical2 (2nd pass) | 655 ns/op, 295 B/op | 1415 ns/op, 1944 B/op | +116% time, +559% generated |
| sloppy | 1333 ns/op, 1562 B/op | 2063 ns/op, 1567 B/op | +55% time, +0% generated |
| mixed | 3174 ns/op, 53 B/op | 5873 ns/op, 754 B/op | +85% time, +1322% generated |

`retained` is ~0 on both sides for every scenario. No leak was introduced.

### Reading this

The regression is real and it is **entirely in deciding whether repair is
needed**, never in copying:

- The copy-on-write fast path is intact. On the canonical fixture
  `prepareSystemOneArgs` returns the *same object* at all three levels — top
  level, the questions map, and each question object. Nothing is copied and
  nothing is retained.
- The cost is the canonicality analysis. Before the change, deciding "nothing
  to do" was one check; now it has to rule out 13 repair rules first, and that
  analysis is what allocates the extra ~1.6 KB of short-lived garbage.
- The repair path itself barely moved: `sloppy` generated 1562 -> 1567 B/op,
  i.e. unchanged. `mixed` is up (53 -> 754 B/op) because it is the fixture that
  actually exercises several repairs.

In context this is negligible: a `system_one` call waits on a network round trip
to the judge, and the absolute delta is ~760 ns and ~1.6 KB of garbage that is
collected immediately.

If this ever needs to come down, the lever is the order of the checks in
`isCanonicalQuestion` and the top-level canonicality test in
`prepareSystemOneArgs` — cheap structural discriminators (is `state` under an
alias key? is `questions` a record?) can short-circuit before the per-question
analysis runs.

## render.bench.ts — renderSystemOneResult()

| scenario | `main` (8cf6ba1) | 1.2.1 | delta |
| --- | --- | --- | --- |
| choice/3 | 132 chars, 341 ns/op | 336 chars, 417 ns/op | +204 chars |
| choice/50 | 1898 chars, 2415 ns/op | 2102 chars, 2850 ns/op | +204 chars |
| choice/255 | 9892 chars, 11135 ns/op | 10096 chars, 13373 ns/op | +204 chars |
| score/5 | 159 chars, 436 ns/op | 429 chars, 424 ns/op | +270 chars |
| multi (choice+noul+score) | 365 chars, 829 ns/op | 635 chars, 849 ns/op | +270 chars |

The size increase is **flat and bounded**: +204 chars per result containing a
choice or noul, +270 per result containing a score, regardless of how many
options or levels are present. It comes from the score legend now being rendered
(it was silently dropped before) plus one closing line per whole result. It does
not scale with answer size, which was the point of emitting the closing line once
per result rather than once per answer.

Throughput is ~20% lower in wall-clock terms, but the output is 2.5x larger for
choice/3, so the per-output-byte cost is nearly unchanged.

The output is model-visible text and larger results cost input tokens on every
later turn of a session. That is the real cost of this change, and it is a
deliberate trade: the previous output dropped a score legend the caller needed to
read the answer at all.
